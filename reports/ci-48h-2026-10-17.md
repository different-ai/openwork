# PR CI: trailing 48 hours, October 17, 2026

## Scope and verdict

Window: **October 15, 2026, 8:42 p.m. through October 17, 8:42 p.m. America/Los_Angeles** (October 16 03:42 UTC–October 18 03:42 UTC).

Retrieved **3,139 unique Actions runs**, including **173 PR change proof runs across 64 PRs**. Read job/step metadata for all 1,744 PR-event/target-event and downstream Evidence review runs, plus 172 PR CodeQL runs.

**Optimize proof execution, not the already-fast build checks.** Proof accounts for 66% of measured PR-related runner time. Its longest successful path is usually the slowest local proof, followed by a whole-matrix barrier and serial screenshot review. Remote core-chat preparation/checkpoint persistence is another independent critical path.

The requested goal is a **50% reduction in PR CI turnaround**. The patch removes identified review/build-cache waste without removing journeys, security checks, engine parity, screenshot assertions, or reopenable checkpoints. A live checkpoint-cache experiment did not improve performance and was discarded. **A 50% end-to-end reduction has not been established.** Component benchmarks must not be represented as an overall CI result.

- Browser interaction/checkpoints: approximately **43 seconds** from world ready through end-state capture.
- End-state screenshot: **21:25:55 UTC**; record closed at **21:29:26 UTC**. Approximately **211 seconds** remained after the screenshot while checkpoint saves/teardown completed. This is not all application testing or all directly proven snapshot transfer time.
- Local proof jobs took 139–255 seconds. Trusted judge jobs took 56–140 seconds; three advisory review steps reached their 120-second cap.

The existing saved-world builder flushes filesystem caches before saving memory; checkpoint forks do not. This suggested an experiment, but the live comparison below did **not** support shipping that optimization.

## Changes implemented

1. **Bound authoritative screenshot judging.** Two screenshot workers per record and two records per invocation; at most four model requests in flight per judge invocation. Each screenshot still describes the image before judging it. Same claims, verdicts, provider-error-to-pending behavior, provenance checks, and capture-order reports.
2. **Bound advisory review to three screenshots per record.** Measure every layout first; atomically persist completed critiques and pending markers through a serialized write queue. Keep all screenshots, findings, the existing 120-second safety cap, and sequential record processing. A hard kill still leaves useful measured/completed evidence.
3. **Publish shared vision-cache entries atomically.** Concurrent judges must never read a partially written cache or corrupt identical keys. Unique temporary files plus rename make publication safe across processes.
4. **Do not invalidate a runtime world for the UI-guardrail checker or baseline.** Only three explicit CI-only paths are excluded; guest runtime/build inputs still invalidate the fingerprint. Both evidence providers share this classifier.

No workflow gate, model, required check, security policy, environment approval, test assertion, or coverage selection was weakened. No production feature behavior was added.

### Rejected optimization: checkpoint cache flushing

Live Daytona A/B, two independent VMs restored from the **same** historical end-state checkpoint, memory-preserving snapshot in both cases:

| Variant | Save time, including trim when enabled | Restore |
|---|---:|---|
| Existing behavior | 157.948 s | Matching checkpoint manifest, evidence service active, 11 Chrome processes |
| `sync` + filesystem cache drop before save | 174.921 s | Same checks passed |

The trimmed variant was **10.7% slower** in this one sequential pair. It reduced guest page cache from approximately 941 MB to 757 MB, not to zero. Provider variation and run order prevent a causal slowdown claim, but there is **no demonstrated speedup**. The implementation and its new tests were removed; checkpoint behavior remains unchanged. All benchmark VMs and snapshots were deleted. This health check does not independently establish a complete signed-in UI interaction after restore.

**Final end-to-end outcome remains unmeasured. The 50% overall target is not achieved/proven by the available evidence.**

## Roll-forward measurement

After deployment, compare matched successful PR proof workloads, not just all run medians:

1. Creation → last runner completion, successful median and P90.
2. Slowest local proof, remote core-chat preparation/body/save/cleanup, and slowest trusted judge separately.
3. Total runner minutes per SHA and cancelled runner minutes.
4. Same journey/engine coverage, pending judgments, provider errors, and reopened checkpoint validity.

The mandatory judge intentionally executes trusted default-branch code. A PR cannot safely run its own changed judge with model secrets. Consequently, PR checks alone do not demonstrate the new trusted judge's live performance before merge.

The latest-day slowest local proof already takes about **4.1 minutes**, before its post-proof judge starts. A 3.5-minute target cannot be justified by optimizing review alone. Further work must reduce that local critical path (for example, safely isolate independent restart scenarios/engine runs) as well as checkpoint persistence. The next pipeline target is the **whole-matrix barrier**: overlap trusted judging of completed proof artifacts with slower producers, preserving immutable run/attempt/SHA/spec binding and the current trusted-code/secret boundary. Do not move secrets into PR-head jobs to gain speed.

## Collection method and limitations

- GitHub REST: Actions runs filtered by creation range, recursively splitting windows above the API's 1,000-result retrieval limit; deduplicate run IDs.
- Read `/actions/runs/{id}/jobs?per_page=100` with pagination. Group standard PR workflows by event/name and CodeQL dynamic runs by `refs/pull/*/head`.
- Map native PR references first, otherwise a unique PR head-branch match against repository PR metadata. All 173 proof runs mapped to 64 PRs.
- This is a cohort of runs **created** within the window, not a clipped accounting of every job second occurring inside the window. Job metadata was collected subsequently, so completed execution can extend beyond the window. Runs started before the window are excluded.
- Timing snapshot is observational and latest-attempt only; reruns may obscure earlier attempts. Cancelled jobs have partial work, unfinished jobs have no complete duration, and recent PRs have less observation time.
- Bounded concurrency raises instantaneous model request concurrency. Rate limits may erode the gain; observe provider errors and pending claims. Advisory reviews may complete more screenshots within the unchanged cap, increasing model work compared with a previously truncated review.
- Assigned-runner elapsed time is not a cost estimate. Different runner sizes/prices and remote VM time are not normalized. Downstream Evidence review includes progress/redundant events; not every one publishes a final report.
- Failure counts are outcomes, not root-cause classifications. This report does not label the failures as flaky or pre-existing.
- Raw responses, logs, downloaded evidence and secret-bearing infrastructure details stay outside the repository; only aggregate public CI measurements are reported here.
