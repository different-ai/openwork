---
title: "Microsoft Entra SAML SSO"
description: "Connect Microsoft Entra ID to OpenWork Cloud or a self-hosted deployment with SAML"
---

Use this guide to let members sign in to OpenWork through a Microsoft Entra
enterprise application. After sign-in works, configure
[Microsoft Entra SCIM provisioning](/cloud/scim-microsoft-entra) if you want to
synchronize members and groups.

## Before you start

You need:

- An OpenWork organization with SSO available (Team or Enterprise on OpenWork Cloud).
- The OpenWork owner, or a member with **Manage single sign-on** permission.
- An Entra administrator who can create and assign enterprise applications.
- Your users' work email domain, for example `example.com`, and DNS access if
  OpenWork asks you to verify it.
- A recovery plan prepared **before** enabling SSO; see [Recovery](#recovery).

Creating an ordinary app registration does not establish permission to create
or manage a non-gallery enterprise application. Confirm those Entra rights
before starting. Keep Entra and OpenWork open in separate tabs.

A saved OpenWork configuration stays disabled until domain verification, a real
authentication test, and explicit enablement are complete.

<Note>
For self-hosted deployments, use the URLs shown in **Settings → SSO**. SAML uses
the OpenWork web/auth origin, for example `https://ow.ai.example.test`, never
the separate API host. Keep `/api/auth` reachable through that web/auth origin.
</Note>

## Setup order

Follow these steps in order. The mapping tables below are **reference**, not a
second sequence of setup steps.

1. **Create the IdP app and pause.** In the Entra admin center, open **Entra ID →
   Enterprise apps**, create a non-gallery application for OpenWork, and select
   **Single sign-on → SAML**. Pause before completing **Basic SAML Configuration**.
2. **Copy the IdP values.** Obtain **Microsoft Entra Identifier**, **Login URL**,
   and the active **Certificate (Base64)** using the [Entra reference](#what-you-need-from-microsoft-entra).
3. **Save in OpenWork.** Open **Settings → SSO**, choose **SAML**, enter those IdP
   values and your users' email domain, leave **Audience URL** blank unless you
   need an override, then save. SSO is still disabled.
4. **Copy OpenWork's generated values back into Entra.** Edit **Basic SAML
   Configuration** using the [OpenWork reference](#what-openwork-gives-you):
   Entity ID → Identifier, ACS URL → Reply URL, Sign-in URL → Sign on URL. Save in Entra.
5. **Configure claims, signing and assignment.** Follow [Claims and Name ID](#claims-and-name-id)
   and [Assign users](#assign-users), including the same administrator who will test.
6. **Verify the domain.** Follow [Set and verify the email domain](#set-and-verify-the-email-domain);
   skip TXT only if OpenWork already shows the domain verified.
7. **Test.** Complete [Test SSO](#test-sso) as the existing OpenWork administrator.
8. **Enable.** Prepare [recovery](#recovery), then follow [Enable SSO](#enable-sso).
   Do not treat saving or a successful test as enablement.

## What OpenWork gives you

Reference for **step 4**, after the first OpenWork save: copy these generated
values into Entra **Basic SAML Configuration**. Newer OpenWork versions group
them under **Give these values to your identity provider**.

| OpenWork value | Entra field | What to enter |
| --- | --- | --- |
| **Entity ID** | **Identifier (Entity ID)** | The OpenWork web/auth origin, for example `https://ow.ai.example.test`, unless you set **Audience URL**; then use that exact audience |
| **ACS URL** | **Reply URL (Assertion Consumer Service URL)** | The complete generated ACS URL, including its organization-specific path |
| **Sign-in URL** | **Sign on URL** | The generated organization sign-in URL, for example `https://ow.ai.example.test/sso/<org-slug>` |
| **Metadata URL** | No manual field required | Optional service-provider metadata for import or checking the configuration |

Use the **ACS URL** card (labelled **ACS URL (REPLY URL)** in newer versions).
**Entity ID** is shown as its own value in newer versions. In older versions,
use the web/auth origin unless **Audience URL** is set; as a fallback, confirm
`EntityDescriptor entityID` in the **Metadata URL** XML. Do not use the Entra
issuer `https://sts.windows.net/<tenant-guid>/` as OpenWork's Entity ID.
Leave Entra **Relay State** blank.

<Warning>
Redirect URL is for OIDC only. For SAML, the Reply URL / Single sign-on URL / ACS
URL in your identity provider must be OpenWork's ACS URL. Older OpenWork versions
also display a Redirect URL card for SAML; do not copy it into Entra.
</Warning>

## What you need from Microsoft Entra

Reference for **steps 2–3**: under **Set up** your application, copy the two
URLs below. Under **SAML Certificates**, download the active **Certificate (Base64)**.

In OpenWork **Settings → SSO**, choose **SAML** and enter:

| Entra value | OpenWork field |
| --- | --- |
| **Microsoft Entra Identifier**, for example `https://sts.windows.net/<tenant-guid>/` | **IdP Issuer URL** |
| **Login URL**, for example `https://login.microsoftonline.com/<tenant-guid>/saml2` | **SAML Entry Point** |
| Active **Certificate (Base64)** | **IdP Certificate** |

Set **Domain** (labelled **Users' email domain** in newer versions) to your
users' email domain, for example `example.com` for `admin@example.com`.
Leave **Audience URL** blank to use the OpenWork web/auth origin; newer versions
place it under **Advanced**. Save, then copy the generated OpenWork values back
into Entra using the table above. Compare the ACS URL character for character.

Entra's **Microsoft Entra Identifier** identifies the identity provider;
OpenWork's **Entity ID** identifies the service provider. They are not interchangeable.
The ACS URL and Sign-in URL select the OpenWork organization, including for
people who belong to more than one organization.

## Claims and Name ID

In Entra **Attributes & Claims**, set the name identifier to the user's stable
work email, with **Email address** format. Use `user.mail` when it contains that
email; use `user.userprincipalname` only if it matches the email in OpenWork.
Do not assume the tenant UPN, a guest `#EXT#` identifier, and the user's email
are the same. If you send a separate `email` attribute, keep it aligned with
NameID and the existing OpenWork account.

For the first authentication test, Entra must return the **same email as the
OpenWork administrator who started the test**, not a different test account.

### Signing

Open **SAML Certificates** and edit the token signing certificate settings:

- **Signing Option**: `Sign SAML assertion`
- **Signing Algorithm**: `SHA-256`

After a certificate change, copy the active certificate into OpenWork again.
Entra can activate a new certificate while you edit settings. Save and retest
after updating OpenWork's certificate.

## Assign users

In the enterprise application's **Users and groups** page, assign the OpenWork
administrator who will run the test. For external users, assign the guest
identity in this tenant and check the email it will send in SAML. Expand
assignments only after the first end-to-end sign-in works.

## Set and verify the email domain

**Domain / Users' email domain** means the part after `@` in the users' actual
email addresses. For `admin@example.com`, enter `example.com`, not the identity
provider's tenant domain such as `<tenant>.onmicrosoft.com`. Only use an
`onmicrosoft.com` suffix if it really is the suffix of the users' email addresses.
Domain verification does not correct an email or NameID mismatch.

<Note>
In OpenWork **v0.18.58**, saving an Entra issuer on `sts.windows.net` or
`login.microsoftonline.com` with a tenant GUID as the first path segment
marks the SSO domain verified automatically. This does not require the email
domain to end in `onmicrosoft.com`. If OpenWork already shows **Domain verified:
Yes**, skip the TXT step. On other versions or when the connection remains
unverified, follow the DNS proof OpenWork displays instead.
</Note>

If verification is required:

1. Select **Request token** under domain verification in **Settings → SSO**.
2. Create a DNS `TXT` record using the exact **Host / name** and token shown.
   Use the short host if your DNS console appends the zone; otherwise use the
   full DNS name.
3. Once the record resolves publicly, select **Verify domain**.

The token expires after seven days. After verification succeeds, you may remove
the TXT record.

## Test SSO

After assignments and domain verification are complete:

1. In **Settings → SSO**, select **Enable Config** or **Enable SSO** to open
   **Test SSO before enabling it**.
2. Select **SSO Login** and complete Entra authentication in the separate window
   as the same OpenWork administrator.
3. Return to OpenWork and confirm **Authentication test successful**. Check
   that the intended organization and existing administrator account are used.

Test links expire after five minutes. The test uses the saved provider and ACS
URL, not a separate test ACS URL. If you edit the configuration, test it again.
Do not enable SSO while a test is failing.

After a failure, correct the cause and select **Try SSO login again** once.
If the dialog still shows **Authentication test in progress**, finish the
existing popup or wait for that test's five-minute expiry. Closing or reloading
the administrator browser can leave that intent in progress until it expires.
Do not click repeatedly or resave a configuration that already passed.

OpenWork allows **IdP-initiated SAML** sign-in. Use OpenWork's built-in test
above before enabling: launching an Entra tile alone does not record the
required administrator test result.

## Enable SSO

Prepare [recovery access](#recovery), then select **Enable SSO** after the
successful test. Saving or testing alone does not enable member sign-in.

<Warning>
On a single-organization self-hosted deployment, enabling SSO stops
email/password sign-in for **everyone, including the owner and the initial
administrator**. The owner's password is not a break-glass bypass. Keep the
current administrator session open while you verify a new SSO sign-in in a
separate browser profile.
</Warning>

In the standard sign-in flow, users with the verified email domain are directed
to organization SSO. This domain routing is separate from the deployment-wide
password block in single-organization mode.

## Recovery

Before enabling SSO, prepare both a recent administrator session and, if your
recovery policy allows it, an organization-scoped API key. The administrator or
key's member must have **Manage single sign-on** (`sso.manage`) permission;
being an Admin without that permission is not enough.

- **Recent session:** use **Settings → SSO** to disable SSO from an authorized
  session signed in within the last **two hours**. Keeping a tab open does not
  extend that window. After it expires, re-authentication is required, which
  may be impossible while the identity provider is unavailable.
- **Pre-created API key:** an authorized organization API key can call
  `POST /v1/sso/disable` on your Den API, using the `x-api-key` header. API keys
  skip the recent-sign-in check, not the permission check. Create and securely
  store the key before rollout; do not put its value in a URL, screenshot, or
  shared notes.

Disabling SSO keeps its configuration and removes the single-organization SSO
password block. Existing password accounts can then sign in, subject to the
normal account and password protections. Fix the configuration, retest, and
explicitly re-enable it. If neither recovery path is available, escalate to
your deployment operator; a forgotten password or the bootstrap setup code
does not bypass enabled SSO.

## Provisioning and roles

Successful SAML sign-in can create organization membership just in time with
the default `Member` role. Password signup alone does not add a user to the
organization or create a SCIM identity. A matching existing account can be
linked through SSO when its identity and email domain match the configuration.

SAML `role`, `groups`, or `admin` attributes do not grant elevated roles. The
owner assigns roles; ownership changes require ownership transfer. For
synchronized groups, configure [Entra SCIM](/cloud/scim-microsoft-entra), then
explicitly approve [Team Admin access](/cloud/members-and-rbac#team-admin-access).

## Troubleshooting

Match the message or error code, then fix the configuration before retrying.
Do not repeatedly submit a failing login.

| Message / code | Check and action |
| --- | --- |
| `AADSTS50011` | Reply URL mismatch. Set Entra **Reply URL (Assertion Consumer Service URL)** to OpenWork's complete **ACS URL**, not its OIDC Redirect URL or separate API host. Match scheme, host, path, and trailing slash exactly. |
| `AADSTS700016` / `Application with identifier … was not found` | Identifier mismatch or wrong Entra tenant. Set **Identifier (Entity ID)** to OpenWork's Entity ID (web/auth origin unless Audience is set); do not use the Entra issuer. Confirm you configured the enterprise app in the tenant used for sign-in. |
| `AADSTS50105` / user not assigned | Assign the test administrator under **Users and groups**. For a guest, check the assigned tenant identity and emitted email. |
| `Invalid SAML response` / `saml_error` | Check the active **Certificate (Base64)** matches OpenWork, sign the assertion with SHA-256, and compare Entity ID and ACS values. Save and retest after changes. |
| `account_not_linked` / `SSO authentication did not complete successfully. Check the provider configuration and try again.` | First check **Domain / Users' email domain**, SAML email / NameID, and the existing OpenWork account email. Use `example.com` for `admin@example.com`, not a tenant-only suffix. These errors can have other causes; inspect server diagnostics if the values match. |
| `SSO authenticated a different account. Sign in at the identity provider with the same administrator account and try again.` | Use the same administrator email that started the test. Switch the account in Entra, not the OpenWork organization. |
| `This deployment is configured for one organization. Additional organization changes are disabled.` | A stale session can hold the wrong active organization. Sign out and sign in again through this deployment's organization **Sign-in URL**. Keep any separate recovery session open. |
| `Verify the SSO domain before testing this configuration.` | Check whether Entra automatic verification applied. If not, complete the displayed DNS TXT proof; do not change the domain to `onmicrosoft.com` just to obtain verification. |
| `The SSO authentication test expired. Start a new test and complete it within five minutes.` | Create a fresh test link and complete it within five minutes. |
| `The SSO authentication window was closed before the test completed.` | Start a new test; keep the authentication window open until it returns or closes itself. |
| `For security, confirm it's you before changing workspace settings.` / `fresh_auth_required` | The two-hour privileged-session window ended. Re-authenticate before changing SSO; if SSO is broken, use the pre-created authorized organization API key. |
| HTTP `429` | Stop retries and honor `Retry-After` when present. Production auth defaults to 20 requests per 60 seconds; email/password sign-in is limited to 5 requests per 5 minutes and can also have failed-password lockouts. Do not confuse the password limit with the SSO test's five-minute expiry. |
| `This deployment uses organization SSO. Continue with SSO to sign in.` | Password sign-in is blocked in single-organization mode, including for the owner. Use the organization **Sign-in URL**, or an existing recovery path to disable SSO. |
| `unsolicited_response` / `IdP-initiated SSO not allowed` | Current OpenWork SAML policy allows IdP-initiated sign-in. Check the running version and provider configuration rather than assuming all IdP-initiated responses are rejected; start from OpenWork's organization **Sign-in URL** while diagnosing. |

For Entra's field definitions, see Microsoft's
[SAML setup guide](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/add-application-portal-setup-sso),
[claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/saml-claims-customization),
and [certificate guide](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/tutorial-manage-certificates-for-federated-single-sign-on).
