---
title: "Microsoft Entra SCIM provisioning"
description: "Provision OpenWork members and teams from Microsoft Entra ID"
---

Configure Microsoft Entra ID to send user and group provisioning requests to
OpenWork's SCIM endpoint. Provisioned security groups can become OpenWork teams
when team synchronization is enabled.

<Warning>
This guide is not backed by a live Microsoft Entra tenant test. Local protocol
simulation is not verification of Microsoft's provisioning service, your tenant,
or SCIM compliance. Complete the connection, mapping, lifecycle, and background
cycle checks below before expanding scope.
</Warning>

For connector security, token rotation, lifecycle checks, and reconciliation,
see [SCIM provisioning](/cloud/scim-provisioning).

## Before you start

You need:

- An OpenWork organization on the Enterprise plan (SCIM), with SSO set up.
- The OpenWork organization owner, or someone granted **Manage SCIM provisioning**.
- A working, domain-verified, tested, and enabled OpenWork SAML connection.
  Complete and test
  [Microsoft Entra SAML SSO](/cloud/sso-microsoft-entra) first.
- A Microsoft Entra role that can manage enterprise applications and
  provisioning.
- An Entra plan that supports assigning groups to enterprise applications if
  you want to synchronize groups.

Do not broaden SCIM assignment scope until you have tested both SAML sign-in and
SCIM. Make sure at least one OpenWork owner can sign in through SAML and that
the current SSO configuration has passed OpenWork's **Test SSO before enabling
it** flow before relying on Entra as the identity source.

## 1. Get the OpenWork connection values

In OpenWork, select the organization you want to connect, then open
**Settings → Auth & Security → User provisioning (SCIM)** (older versions: **Settings → SCIM**).

Confirm that the page shows **SAML/SSO active**, then:

1. Select **Create connector**. If a connector already exists, select
   **Rotate token** only when you intend to replace its current secret.
2. Copy the **SCIM base URL**.
3. Copy the **SCIM bearer token** immediately. OpenWork shows the full token
   only after creating or rotating it.
4. To synchronize Entra groups as OpenWork teams, select **Enable team sync**
   under **Create teams from SCIM groups**.

You will enter these values in Entra:

| Entra field | Where to get the value |
| --- | --- |
| Tenant URL | OpenWork **Settings → Auth & Security → User provisioning (SCIM) → SCIM base URL**. It normally ends in `/api/auth/scim/v2`. |
| Secret Token | The one-time **SCIM bearer token** shown after you create or rotate the connector. |

Use the displayed base URL unchanged, including its hostname. It may use a
different origin from the API in a split-host deployment. Entra must be able to
reach it over HTTPS.

Treat the bearer token like a password. Do not put it in tickets, screenshots,
logs, or shared setup notes. Rotating it immediately invalidates the previous
token, so update Entra at the same time. Enter the OpenWork token in **Secret
Token**; do not leave the field blank or substitute a Microsoft Graph token.

## 2. Configure provisioning in Entra

In the [Microsoft Entra admin center](https://entra.microsoft.com):

1. Open **Entra ID → Enterprise apps**.
2. Select the same enterprise application used for OpenWork SAML SSO.
3. Open **Provisioning**.
4. Select **Get started**, then choose **Automatic** provisioning.
5. Open **Connectivity** or **Admin Credentials**, depending on the Entra
   interface shown for your tenant.
6. Paste the OpenWork **SCIM base URL** into **Tenant URL**.
7. Paste the OpenWork **SCIM bearer token** into **Secret Token**.
8. Select **Test Connection** and wait for a successful result.
9. Save the configuration.

If **Test Connection** fails, confirm that the URL has no extra path or trailing
text and that the token has not been rotated since it was copied.

## 3. Review mappings and scope

Open **Attribute mapping** in the provisioning configuration. Review the
**Users** mapping first. Enable the **Groups** mapping only if you intend to
provision group objects. Assigning a group to scope user provisioning and
provisioning the group itself are separate choices.

Start with a small set of mappings and verify each one:

| SCIM target | Mapping to review |
| --- | --- |
| `userName` | A stable, unique work email from `userPrincipalName` or `mail`; use it as the initial matching attribute. |
| `emails[type eq "work"].value` | The same person's work email. Confirm it agrees with the identity used for SSO. |
| `displayName` or `name.formatted` | The name you expect in OpenWork **Members**. Test an update, not just the initial value on create. |
| `active` | Entra's lifecycle mapping, including disable and restore. Keep the user **Update** action enabled. |
| Group `displayName` and `members` | A unique group name and direct user members, if group provisioning is enabled. |

Do not assume every default Entra mapping is supported. Add enterprise-extension
or other optional attributes only after testing their exact request shapes on
your deployment. Changing the matching attribute also changes how Entra locates
existing users; do not make that change casually after provisioning starts.

For a controlled rollout, set **Scope** to **Sync only assigned users and
groups**. This limits provisioning to identities assigned under the enterprise
application's **Users and groups** page.

Use a stable, unique email address for the SCIM user name. If your Entra user
principal names use an `onmicrosoft.com` domain but users sign in to OpenWork
with another email domain, verify which Entra attribute is mapped to
`userName`. Keep the SAML NameID and SCIM identity consistent so Entra does not
create a second OpenWork member for the same person.

### Existing OpenWork accounts

SCIM can link a matching existing account only when the user is already an
active member of the connector's OpenWork organization. The account keeps its
existing user ID; provisioning does not grant a new organization role.

An existing account with no active membership in that organization returns
`409 Conflict` instead of being linked by email alone. Membership in another
organization, a removed membership, or a pending invitation does not qualify.
An authorized administrator must establish active membership through the normal
onboarding process before retrying. Brand-new accounts follow the normal SCIM
provisioning flow.

## 4. Assign test users and groups

In the enterprise application, open **Users and groups** and select **Add
user/group**.

Start with:

- One or two test users who can sign in through the configured SAML app.
- One assigned security group containing those users.

Assignments control which objects are in scope when provisioning is set to
**Sync only assigned users and groups**. Creating a group elsewhere in Entra is
not enough; assign it to the OpenWork enterprise application as well.

## 5. Test with Provision on demand

Open **Provisioning → Provision on demand**.

Test a user first:

1. Search for and select an assigned test user.
2. Select **Provision**.
3. Confirm that import, scope evaluation, matching, and the final action all
   succeed.
4. In OpenWork, open **Members** and confirm that the member appears with the
   expected email.

Then test a group:

1. Make sure the test group already contains at least one assigned test user.
2. Search for and select the assigned group.
3. Under **Selected users**, explicitly select up to five members to include in
   the on-demand test.
4. Select **Provision**.
5. Open the result's **Group membership operations** tab and confirm each member
   shows **Add member — Success**.
6. In OpenWork, open **Members → Teams** and confirm that the group appears as a
   SCIM-managed team with the expected members.

<Note>
Microsoft documents a limit of five selected members for on-demand group
provisioning. This does not test the group's full membership. On-demand
provisioning also has restore and nested-group limitations; use a regular
background cycle for lifecycle validation. See Microsoft's
[on-demand provisioning guide](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/provision-on-demand).
</Note>

## 6. Start scheduled provisioning

After the on-demand tests pass:

1. Return to **Provisioning → Overview**.
2. Set **Provisioning Status** to **On**, or select **Start provisioning** in
   the newer Entra interface.
3. Save the change.
4. Check **Provisioning logs** after the first cycle completes.
5. Refresh OpenWork **Members** and **Teams** to verify the final state.

Regular provisioning is incremental. A newly assigned object might not appear
until the next cycle; use the Entra provisioning logs to distinguish a pending
cycle from a failed operation.

## Verify lifecycle changes

Before expanding the assignment scope, verify the complete lifecycle:

1. Change a test user's mapped name. Confirm the provisioning log succeeds and
   the new name appears in OpenWork **Members**.
2. Remove a test user from a synchronized group while keeping them assigned to
   the application through a separate assignment. Confirm the team loses the
   member without unintentionally removing organization access.
3. Disable or unassign a test user. Wait for a successful background provisioning
   update and confirm active organization access is removed.
4. Verify that the disabled SCIM user is still readable with `active=false` at
   the same ID. Reactivate or reassign the user, then confirm the background
   cycle restores that same ID with `active=true`. Test sign-in separately.
5. Add another assigned group and verify its team and direct membership.
6. Confirm an unrelated user's access remains unchanged.

Use the [complete lifecycle checklist](/cloud/scim-provisioning#validate-the-complete-lifecycle),
including the version-dependent disable/restore check. Lifecycle corrections are
pending release; these are checks to perform, not a claim that the deployed
service already passes them. Do not use a new user creation as proof that
reactivation worked. Test permanent deletion separately
from a temporary disable.

Change SCIM-managed teams in Entra, not in OpenWork. OpenWork keeps manually
created teams separate from identity-provider-managed teams.

### Optional: grant organization Admin through an Entra group

After verifying the synchronized membership, the OpenWork organization owner
can approve the team to grant organization `Admin`. The Entra group name and
SAML group attributes do not grant elevated access by themselves. Follow
[Team Admin access](/cloud/members-and-rbac#team-admin-access) for approving the team,
membership controls, and reapproval rules when team sync is disabled or re-enabled.

Test with a member who has no direct Admin role or other Admin team grant:
confirm **Admin via** the synchronized team, remove them from the Entra group, wait for
successful provisioning, and confirm that inherited access is gone. Review
**Provisioning logs** if the change is still pending.

## Operate and troubleshoot

Check Entra **Provisioning logs** for each outbound action and OpenWork's SCIM
tab for local sync issues. Entra schedules and retries its own provisioning jobs;
OpenWork's **Run reconciliation** checks local identity state, not Microsoft's
directory. It does not start an Entra cycle or resolve quarantine in Entra.

For safe [token rotation and connector removal](/cloud/scim-provisioning#rotate-or-remove-the-connector),
coordinate changes with the Entra administrator rather than deleting the
connector to troubleshoot a single failed user.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| **Test Connection** fails | Incorrect Tenant URL, stale token, copied whitespace, or an unreachable endpoint | Use the advertised HTTPS base URL and current OpenWork token. Check the HTTP status before rotating again |
| User or group is not found in **Provision on demand** | The object is outside the provisioning scope | Assign it under the enterprise application's **Users and groups** page |
| Entra will not allow a group assignment | The tenant plan does not support assigning groups to enterprise applications | Enable a suitable Entra plan or test with directly assigned users |
| On-demand group provisioning does not test membership | No users were selected, or members are outside scope | Select up to five direct members, verify their assignment, and inspect the failing stage before retrying |
| A group provisions but no OpenWork team appears | OpenWork team synchronization is disabled | Open **Settings → Auth & Security → User provisioning (SCIM)** and enable **Create teams from SCIM groups** |
| Entra creates a duplicate OpenWork member | SAML and SCIM use different email identifiers | Align the SAML NameID and the SCIM `userName` mapping |
| A profile update fails with `400` | An unsupported attribute or request shape on the deployed version | Inspect the failing mapping and returned error. Verify `displayName` and `name.formatted` separately rather than assuming operation casing is the cause |
| Reactivation fails with `404` | The original SCIM resource is no longer available | Stop expanding scope and review the deployed version and disable/restore test; do not silently replace it with a new user |
| Entra reports success but OpenWork still shows the old state | A stale view, a different mapped attribute, or incomplete local synchronization | Refresh OpenWork, compare the actual exported attributes in **Provisioning logs**, and review OpenWork SCIM health |
| The provisioning job is quarantined | Repeated failures in Entra's job | Resolve the reported credentials, mappings, or endpoint errors in Entra. OpenWork reconciliation does not clear provider quarantine |

For member and team behavior after provisioning, see
[Members and RBAC](/cloud/members-and-rbac).
