---
title: "Create the first administrator"
description: "Securely claim a new private OpenWork deployment without enabling public signup."
---

A private deployment should start with public signup disabled. Configuring an email in the owner or platform-admin allowlist authorizes that identity after authentication; it does not create an account, choose a password, or generate a default administrator password.

Releases that include initial-administrator bootstrap provide a dedicated setup page at:

```text
https://<your-den-web-host>/setup
```

<Warning>
  Chart and image versions without `/setup` do not support this private bootstrap flow. Upgrade before attempting first-user setup. Entering an allowlisted email on the normal sign-in page cannot create a missing account.
</Warning>

## Before installing

1. Configure the initial administrator email as an eligible singleton-organization owner (`DEN_SINGLE_ORG_OWNER_EMAILS` on Den API).
2. Add the same email to the platform-admin allowlist only if that person also needs deployment-wide `/admin` access.
3. Generate a unique one-time setup code.
4. Inject the code through a Kubernetes Secret or your platform's secret store as `DEN_INITIAL_ADMIN_BOOTSTRAP_CODE`, or mount it from a file and set `DEN_INITIAL_ADMIN_BOOTSTRAP_CODE_FILE`.
5. Keep public signup disabled.

The setup code is a plain secret string, not a hash or token generated by OpenWork. Never place the real setup code in a committed Helm values file, ConfigMap, container image, source-control file, support ticket, screenshot, logs, or PR.

### Docker Compose evaluation stack

The [evaluation stack](/self-host/evaluate-with-docker-compose) passes the same two Den API variables through `OPENWORK_OWNER_EMAILS` and `OPENWORK_SETUP_CODE`. Set them in the `.env` file beside `docker-compose.eval.yml`, together with `OPENWORK_ALLOW_SIGNUP=false`, before the first `docker compose up`:

```bash
printf 'OPENWORK_ALLOW_SIGNUP=false\nOPENWORK_OWNER_EMAILS=%s\nOPENWORK_SETUP_CODE=%s\n' \
  'admin@example.com' "$(openssl rand -hex 16)" >> .env
docker compose -f docker-compose.eval.yml up -d --wait
```

Then open `http://localhost:3005/setup` and continue with [Complete setup](#complete-setup). The `.env` file holds the real setup code, so keep it private and do not commit it.

## Complete setup

1. Wait until Den web, Den API, and the migration Job are healthy.
2. Open `/setup` on the Den web hostname.
3. Enter the configured administrator email and the one-time setup code.
4. Choose the administrator's name and a password of **8–32 characters**. The
   maximum is **32 characters**, including for a generated password. Include
   uppercase and lowercase letters, a number, and a special character; normal
   password-strength and compromised-password checks still apply.
5. Confirm that OpenWork opens the **installation/onboarding page** (`/install`)
   with the administrator signed in to the singleton organization.

The setup flow uses the existing Better Auth password and session protections. Successful setup creates the first account, creates or claims the singleton organization, grants the configured owner and platform-admin roles, and makes setup unavailable because the deployment now has a user.

## Verify the boundary

After setup:

- revisiting `/setup` reports that setup is complete or unavailable;
- the one-time code cannot create another administrator;
- unknown users still cannot sign up;
- before SSO is enabled, the administrator can sign out and use normal password sign-in;
- restarting or scaling Den API does not re-enable setup.

If the deployment already contains a user, bootstrap remains unavailable even if its setup Secret still exists. Rotating or restoring the Secret does not reopen setup and is not an SSO recovery method.

## Configure SSO next

Configure SAML or OIDC SSO for workforce access, test it as the existing owner,
then configure SCIM if needed. For SAML, follow the
[Microsoft Entra](/cloud/sso-microsoft-entra),
[Google Workspace](/cloud/sso-google-workspace), or [Okta](/cloud/sso-okta) guide.
For an OpenID Connect client, use the [OIDC SSO guide](/cloud/sso-oidc).
Use the URLs shown in **Settings → SSO**: SAML's ACS URL uses the web/auth origin,
not a separate API host. Set **Domain** (labelled **Users' email domain** in newer
versions) to the part after `@` in the owner's and users' actual email addresses,
not the identity provider's tenant domain.

<Warning>
On a single-organization deployment, enabling SSO stops email/password sign-in
for **everyone, including the initial administrator and the owner**. The first
owner is not a password break-glass account after enablement. Password reset,
the owner allowlist, and the one-time bootstrap code do not bypass enabled SSO.
</Warning>

## Prepare recovery before enabling SSO

1. Confirm the first owner's SSO identity returns the **same email** as their
   existing OpenWork account. Complete OpenWork's authentication test before
   selecting **Enable SSO**. A test link expires after five minutes.
2. Keep an authorized administrator session open while you verify a fresh SSO
   sign-in in a separate browser profile. Disabling SSO requires **Manage single
   sign-on** (`sso.manage`) permission and a session signed in within the last
   **two hours**. An open tab does not extend that window; after it expires,
   OpenWork requires re-authentication.
3. If your recovery policy allows it, create and securely store an
   organization-scoped API key **before** rollout. The key's member must have
   **Manage single sign-on** permission. An Admin role alone does not guarantee
   that permission. API keys bypass the recent-sign-in check, not authorization.

If SSO fails, disable it in **Settings → SSO** using the recent authorized
session, or call `POST /v1/sso/disable` on your Den API with the pre-created,
authorized organization API key in the `x-api-key` header. Disabling keeps the
configuration and removes the single-organization password block, so existing
password accounts can sign
in subject to normal account and password protections. Correct the settings,
retest, and explicitly re-enable SSO.

If neither path is available, escalate to your deployment operator. Do not rely
on being able to create a recovery key after you are locked out. Protect
recovery credentials according to your organization's access-control policy;
never put API-key values in URLs, screenshots, or shared notes.
